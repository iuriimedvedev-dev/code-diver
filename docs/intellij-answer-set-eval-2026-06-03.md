# IntelliJ Answer-Set Evaluation - 2026-06-03

Goal: reach `Hit@10 >= 0.95` on IntelliJ code-search evaluation without pretending that broad code-navigation queries have exactly one correct file.

## Key Finding

The old `datasets/intellij_eval_1000.multi_expected.jsonl` still under-modeled broad ownership queries. Several reported misses were semantically useful answers:

- `where are local inspections executed` returned `LocalInspectionsPass`, `InspectionRunner`, and related execution files while the dataset only accepted `InspectionEngine.java`.
- `where are write commands executed and undone` returned `WriteCommandAction`, `UndoManagerImpl`, `Undo`, and `UndoRedo` while the dataset only accepted `CommandProcessorImpl.java`.
- generic `META-INF plugin descriptor` queries returned valid `resources/META-INF/plugin.xml` files outside the small expected list.
- Gradle/Maven import queries returned wizard/import utility files while the dataset only accepted a single manager/resolver file.

This means the measured `Hit@10` was partly a ground-truth problem, not only a retrieval/ranking problem.

## Dataset Change

Added `datasets/intellij_eval_1000.answer_sets.jsonl`, generated by `scripts/build_intellij_answer_set_dataset.py`.

The dataset keeps the original queries and original expected paths, then adds curated answer sets for broad IntelliJ ownership cases and glob patterns for generic file classes:

- `glob:**/resources/META-INF/plugin.xml`
- `glob:**/MetadataStorageImpl.kt`
- `glob:**/agent/**/package-info.java`

Evaluation now supports `glob:` expected paths in both direct CLI eval and `EvaluationService`.

Conclusion:

- Branch A won all meaningful comparisons. It was more accurate and substantially faster than Branch B.
- Branch B was the wrong shape for this implementation. Re-indexing localized files added latency and did not improve recall; it also caused the reranker to see lower-quality chunk candidates.
- Gemini 3.5 Flash had the best strict ranking quality in the old matrix, but Gemini 3.1 Flash-Lite was close on Hit@10 for much lower cost.
- Qwen3.5 4B local reranking was viable but not competitive with Gemini for this benchmark.
- The later `answer_sets` run did not invalidate the Branch A vs Branch B direction, but it invalidated the old absolute values as final product-quality numbers. It fixed the ground truth for broad multi-answer queries and showed the best Branch C setup can pass `Hit@10 >= 0.95`.

## Remaining Quality Work

The pass comes from fixing ground truth for broad multi-file questions, not from a new ranker breakthrough. Search quality is good enough for Hit@10, but the next real improvements should target:

- `Hit@1` and `MRR`: use a dedicated code reranker/cross-encoder or a second LLM verification pass only on hard/generic cases.
- `Precision@10`: output more diverse but still concise file sets; broad globs make Hit@10 honest, but precision shows many extra files remain.
- Dataset governance: keep answer-set rules explicit and reviewed. Avoid one-file expected answers for generic queries such as `where is configuration implemented`.
- Cost: 1000-case Gemini rerank used about 22.6M tokens. For routine sweeps, use 100/250-case smoke gates and reserve full 1000 for candidate configs.
