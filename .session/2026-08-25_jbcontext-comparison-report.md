# code-diver vs JetBrains jbcontext — IntelliJ Community comparison report

Date: 2026-08-25 (extended same day). Scope: apples-to-apples head-to-head on IntelliJ
Community, methodology, full results, the confounds checked before trusting the headline
number, a stage-level root-cause analysis of the "where"-category shortfall, a second
comparison on a harder multi-file-answer dataset, and the outcome of two ranking-fix attempts.

## 1. Setup

- Corpus: IntelliJ Community, commit `693e76f0a37ade9509c9edcf505c446672c9c0b1`, both tools
  indexed against the identical revision.
- Dataset: `datasets/intellij_eval_1000.answer_sets.jsonl`, expanded 1000 → 1065 cases this
  session by hand-writing and file-verifying 65 new realistic "where-*" queries (no fabricated
  paths — every path checked against a live file index of the checkout). Category sizes:
  `symbol-*` 329, `config-*` 329, `path-*` 328 (all three mechanically generated by tokenizing
  the target file's own name/path), `where-*` 79 (hand-written, realistic developer questions,
  up from 14 before this session).
- code-diver config: `configs/intellij/intellij-h46-preserve-top.yml` (current champion).
- jbcontext version: 0.9.10.670 (native macOS arm64 binary), CLI wrapper at
  `~/.jbcontext/bin/jbcontext`.
- Harness: `scripts/compare_jbcontext.py` — scores jbcontext's raw chunk results with the
  exact same file-level metric formulas as code-diver's own evaluator
  (`src/code_diver/services/evaluation_service.py`), so numbers are directly comparable.
  Supports `--revision` (pin jbcontext to the indexed snapshot) and `--reranker {OFF,FAST,BEST}`
  (see finding below).
- **Execution discipline**: every run (code-diver eval, and each jbcontext reranker variant)
  was run solo, full dataset (1065 cases), strictly sequential — never two evaluation processes
  concurrently, per explicit standing instruction (concurrent runs measurably skew each other's
  latency/perf numbers).

## 3. Finding: jbcontext's undocumented `--reranker BEST` mode is a no-op in this environment

`jbcontext search` has an undocumented `--reranker {OFF,FAST,BEST}` flag (absent from
`--help`, recovered via `strings` on the native binary). The silent default when the flag is
omitted is `FAST`. Investigated because the user asked whether jbcontext has a hidden
"turbo/effort" setting we might be under-using.

Verified via `jbcontext --enable-local-logging search ... --reranker BEST -v`: the log
consistently prints `Reranker (best): Nms, K candidates -> K results, 0 reordered` — reproduced
on every manually tested query. Diffing `retrieved_files` between the full OFF and BEST runs
gave **1065/1065 byte-identical result lists**. Conclusion: in this build/account (no visible
error, just silently inert), `--reranker BEST` costs extra latency (mean +564ms vs OFF) and
changes nothing. The only jbcontext reranker mode that does real work is `FAST` (the default) —
it measurably improves over OFF (+0.047 recall@10, +0.064 ndcg@10). **The fair "jbcontext at
its best" config for this comparison is therefore its own default, not the nominally stronger
BEST flag** — most real users would never discover this flag exists anyway.

Also discovered: jbcontext calls a remote endpoint (`api.jetbrains.ai`) even for local-project
search, and hit 4 HTTP 429 rate-limit failures during the FAST run (infra noise, evenly spread,
not a quality signal, but it does mean jbcontext's latency numbers include a network round trip
that code-diver's fully-local pipeline does not).

## 5. Standing caveats (disclose every time this comparison is cited)

1. **Tuning asymmetry**: code-diver's champion config was iteratively hillclimbed against this
   exact 1000/1065-case dataset across experiments H38–H49. jbcontext never saw this dataset.
   The mechanical-category dominance is partly a "home turf" effect, not purely capability.
2. **Stale ground truth**: 8.4% of cases have at least one expected file that no longer exists
   at the current repo revision (moved/deleted since the dataset was built). Caps achievable
   recall symmetrically for both tools — doesn't bias the comparison between them.
3. **Latency is architecturally apples-to-oranges**: jbcontext is a cloud service hitting a
   prebuilt remote index; code-diver computes retrieval + cross-encoder rerank locally, from a
   cold-ish process, per call. Not a fair "which is faster to ship" comparison as measured.
4. **Answer-axis (RAG generation, not just retrieval) has never been externally validated** —
   this comparison is retrieval-only. jbcontext's actual product surface (in-IDE chat) may
   differ materially from this CLI-search-only comparison.

## 6. Root-cause of the "where"-category shortfall (deep stage-level investigation)

Launched a dedicated agent to find, stage by stage, why code-diver loses the "where" (realistic
developer-question) category to jbcontext while dominating everywhere else. Pipeline stages
checked: dense vector retrieval, BM25/fusion scoring, graph propagation (OFF for IntelliJ),
cross-encoder rerank window.

**Headline finding — this bucket's failure shape is NOT the same as the aggregate H48 finding.**
H48 (2026-08-25, whole 1000-case set) found the recall@10 shortfall splits ~74.4% ranking loss
(the right file is retrieved but ranked >10) vs ~25.6% pool-absence (the right file never enters
the candidate pool at all, ceiling `file_recall@200` = 0.9665). A live 6-case sample drilled into
specifically the "where" bucket found a materially different profile: **~100% ranking loss, 0%
pool-absence** in that sample — the correct files are being retrieved, just not ranked in the
top 10. So the fix target for "where" is purely ranking/scoring, not indexing or pool depth.

**Confirmed dominant failure mode: "sibling-family cannibalization".** Multiple files in the
same directory (e.g. a Handler/Dialog/Processor triplet implementing one IntelliJ feature) share
enough path and symbol tokens that `path_score` and `symbol_score`
(`src/code_diver/strategies/hybrid_candidate_scorer.py:32-44`, coverage-fraction-of-query-terms
scoring) come out nearly identical across the whole family — providing zero discrimination for a
paraphrased query. The one semantically load-bearing word in the query (e.g. "coordinated",
"managed" — an intent verb) frequently doesn't appear in any candidate's path/symbol tokens at
all, so it contributes nothing to fusion, and the tie is broken arbitrarily among the sibling
family rather than toward the actually-correct member.

**Other stage-level suspects found, ranked by confidence, not yet acted on:**
- **H-B-adjacent** (acted on, see §9): cross-encoder rerank only reranks
  `candidates[:34]` (`cross_encoder_rerank_retrieval_strategy.py:32-34`) — if base fusion ranks
  the correct file below 34th, the reranker never sees it regardless of its own quality.
- **H-D** (not implemented, lower confidence): `hybrid_query_analyzer.py:14-24` keeps low-signal
  "intent verb" tokens (`min_token_length: 3` lets through words like "coordinated"/"managed"
  that match nothing in path/symbol space and just dilute lexical scoring) — candidate for
  stopword/verb filtering or down-weighting in a future pass.
- **H-C** (not implemented, lower confidence): `openai_embedding_provider.py` /
  `sentence_transformers_embedding_provider.py` enforce `max_input_chars: 500` truncation on the
  embedded text — plausible but unverified as a contributor for this specific bucket.

## 8. Ranking-fix attempts on the "where" bucket: two hypotheses tested, both refuted (honest null result)

Given §6's root cause (sibling-family cannibalization + rerank-window truncation), two concrete,
config-gated, off-by-default fixes were implemented and validated on the 79-case where-only
subset (`datasets/intellij_eval_where_only.jsonl`, for fast ~2-3min iteration):

- **H-A — family-size penalty** (`hybrid_retrieval_strategy.py`): groups candidates into
  "families" per scoring field (path/symbol/symbol_match) and dampens each field by
  `(min_family_size / family_size) ** strength` once a family is large enough. **Refuted**: it is
  mathematically inert for the dominant real failure shape, because the *correct* file is itself
  a member of the large tied family being dampened — uniformly dampening an identical field value
  across an entire family cannot reorder members within that family. No net improvement on
  recall@10/hit@1/ndcg@10; degraded most metrics elsewhere.
- **H-B — widen-on-uncertain rerank window** (`cross_encoder_rerank_retrieval_strategy.py`):
  widens the candidate fetch/rerank limit beyond 34 when the score margin between rank 1 and a
  configurable check-rank is below a threshold (signaling base-fusion uncertainty). **Refuted at
  both original and aggressive threshold settings**: the aggressive setting nudges recall@10 up
  slightly but at the cost of regressing hit@1/MRR, and — more importantly — the `fetch_limit`
  widening fires *unconditionally* in the current implementation whenever the feature is enabled,
  regardless of whether the per-query gate condition itself ever triggers (it triggered on only
  ~8/79 ≈ 10% of where-queries at the original threshold), meaning every query pays the widened
  fetch's latency cost even on the ~90% where it does nothing (+124% p95 latency in the aggressive
  arm).

Both features are implemented as config-gated additions defaulting to `false`
(`family_penalty_enabled`, `widen_when_uncertain_enabled` — see `hybrid_search_config.py`,
`cross_encoder_rerank_config.py`), verified via a full passing test suite (1083 passed, 3
skipped) and a diff-empty champion config (`configs/intellij/intellij-h46-preserve-top.yml`
untouched) — so this is a safe, reversible null result, not a regression. Experiment configs kept
for reference: `configs/intellij/intellij-h49-family-penalty.yml`,
`configs/intellij/intellij-h49-widen-gate.yml`.

**Conclusion**: neither fusion tie-breaking nor rerank-window truncation is the real lever. The
evidence points to the discrimination gap being upstream, in the vector/cross-encoder model's
ability to separate paraphrastic queries from structurally-similar sibling files — a different
class of fix (embedding/reranker model choice, or query-side disambiguation such as query
rewriting/expansion before dense retrieval) than either H-A or H-B addresses. Tracked as an open
follow-on (task tracker #59), not yet scoped into concrete hypotheses.

## 11. Opus deep-research pass: corrected root cause and ranked hypotheses (2026-08-26)

A dedicated Opus-model research agent was tasked with root-causing the where-bucket ranking
weakness in more depth, grounded in cited external literature (Set-Encoder, Setwise, Qwen3
technical report, CoREB, SweRank, InSeNT/ConTEB, SACL — see the agent's own citations for full
references). It **overturned and corrected** the §6 "sibling-family cannibalization" framing
with more rigorous live evidence. This section supersedes §6 where they disagree.

**Pipeline correction**: the active IntelliJ strategy is `graph_file_cross_encoder` =
`CrossEncoderRerank(GraphFileRetrievalStrategy(HybridRetrievalStrategy(vector)))`. Pre-rerank
ranking is driven by `graph_file_search`'s own weights (vector 0.25 / lexical 0.25 / path 0.20 /
symbol 0.10), where that stage's "vector_score" input is *already* the fully-fused hybrid score
— meaning the dense embedding's effective share of the final pre-rerank score is only ≈0.10, not
≈0.42 as previously assumed.

**Corrected root cause — "name-echo distraction," not directory tie-breaking**: of wrong files
appearing in top-10 for where-queries, 85.7% have a basename echoing a query token; only 19.5%
share a directory with the expected file. The dominant failure is repo-wide lexical echo, not
same-directory tie-breaking.

**Deeper cause — the index has almost no natural-language prose to match against**: the embedded
per-file document representation is dominated by path/package tokens. `file_manifest` records
(weighted ×1.08 in the champion) spend 75.7% of their 500-char budget on path/package/directory
tokens, keeping only ~1.7 of ~18.8 real symbols per file on average; `file_summary` is somewhat
richer (22.8% preamble, 4.9/34.2 symbols kept). **The dense vector channel is functionally a
fuzzy filename/path index, not a semantic channel** — this is why intent-verb query terms
("coordinated", "managed") match nothing in the index. The cross-encoder reranker was confirmed
live as "saturated, not broken": on a real query only 1.3% dynamic range separates the correct
file's score from a wrong sibling's — it has nothing semantically differentiating to judge
because the documents it's given are almost entirely path/signature strings.
`recall@200` (pool ceiling) = 0.9241 vs `recall@10` = 0.503 on the where-bucket confirms this is
~100% a ranking/representation problem, not a candidate-pool-depth problem.

**Config-loader bug found and independently confirmed** (`config_loader.py`): `mapping.get(key,
Defaults.X)` applies defaults when a key is *absent* from config — so the champion's own comment
claiming embedding prefixes were "deliberately NOT ported" is factually wrong. `query_prefix`/
`document_prefix` silently inherit EmbeddingGemma-style default templates even though the model
in use is Qwen3-Embedding, which has a different native template convention. See §12 (H-5) for
the fix and validation.

**Scanner test-exclusion bug quantified**: `**/test/**`/`**/tests/**` patterns miss `testSrc/`,
`testSources/`, `platform-tests/` — exactly 7,026 of 75,348 indexed files (9.3%) are test files
that escape exclusion; fixing it would drop the corpus to 68,322 files. Not yet fixed (task #64
does not cover this — needs its own tracker item if prioritized).

**Diagnostic experiments run (both null, informative, not promoted)**: `intellij-h50-vector-lean`
(de-weight path/symbol 4x, up-weight vector 2.2x at the `graph_file_search` stage) — all metric
deltas' bootstrap CIs span zero. `intellij-h50b-dense-only` (strip everything but the dense
vector channel) — only −0.084 recall, not significant, meaning vector/BM25/path/symbol are
effectively redundant/measuring the same signal today.

**7 ranked hypotheses** (highest impact first): **H-1** re-index with LLM-generated
differentiating file-purpose prose (must explicitly ask for *differentiation from neighbors*,
not generic summary — shared-context prepending is shown in cited literature to regress
in-document discrimination up to 53%) — see the throughput feasibility study below, this is a
one-time/incremental job, not a per-run operation. **H-2** raise `max_input_chars` /
reconsider `file_manifest` weight — see §12, blocked. **H-3** listwise/setwise reranking with an
explicit comparative instruction — not yet attempted. **H-4** route-conditional weights at
`graph_file_search` — lower priority per the H50 null results. **H-5** fix `query_prefix`/
`document_prefix` mismatch — see §12, done, mixed result. **H-6** same-directory hard-negative
LoRA fine-tune of the embedder — likely premature, fixes the wrong layer before H-1/H-3. **H-7**
fix the test-file scanner exclusion (see above). Explicitly ruled out with cited evidence: query
rewriting/HyDE/expansion (measured −9 to −12 nDCG@10 for this model class), MMR/diversity
reranking (−20 to −25% nDCG@10), and simply scaling to a larger embedding/reranker model
(Qwen3-Embedding 0.6B→8B is only +1.65 CodeSearchNet, and the 8B model ranks 10th of 11 on the
one benchmark, CoREB, that measures hard-negative intrusion).

**H-1 throughput feasibility (measured, not estimated)**: real IntelliJ Community indexed file
count = 75,348 (cross-checked against the live Qdrant collection). A 10-minute full re-index
needs 125.6 files/sec / 75,348 tok/s prefill / 7,535 tok/s decode. Measured on this machine
(Apple M3 Max, 16 CPU / 40-core GPU / 64GB, llama.cpp+Metal, Gemma-3n E2B QAT Q4_K_XL — the
smallest ready local instruct model available): serial 1.23 files/sec, best batched (16-way)
2.07 files/sec, 130 tok/s decode — **~50-60x too slow**; a full pass would take ~10.1h batched or
~17h serial. Apple Silicon's unified-memory GPU is bandwidth-bound, not compute-bound, for
decode — batching plateaus fast (8→16 concurrency only +14%). **Recommended mitigation**: treat
H-1 as a one-time/rare background job plus incremental, content-hash-keyed caching (only
re-summarize files whose content changed) — sampled 50 real IntelliJ commits show a median of 3
changed files/commit (max 27), so ongoing incremental updates would be trivially fast (~22s
worst case in that sample). H-1 remains open (task #62), not yet implemented.

1. **1800 chars** (verified safe against a 50-doc sample, 21% margin) — failed at batch 0/1177,
   ~3 min in, HTTP 400 "maximum context length is 512 tokens."
2. **1200 chars** (the codebase's own documented default, ~33% margin from the observed failure

Diagnosis: the Java/Kotlin/XML corpus contains files (scattered throughout, not one outlier)
whose content tokenizes far denser than the 50-doc safety sample suggested (plausibly
generics-heavy signatures / manifest lines where `<>,.` punctuation splits into many BPE tokens
per character). Raw character-count truncation is not a reliable proxy for the embedder's hard
512-token ceiling on this corpus, and `cmd_index` has no per-item retry/catch — one oversized
item aborts the entire ~150k-item build, costing real wall-clock (3 min + 48 min = ~51 min spent
on two failed builds). **No metrics obtained for H-2.** Two paths forward, neither executed:
(a) retry once more at a more conservative value (e.g. 900, not guaranteed safe either), or
(b) the technically correct fix — token-aware truncation in `_bounded_prefixed`/
`embedding_text_preparer.py` (tokenize-then-truncate against the real tokenizer, or
catch-and-shrink-and-retry per item). (b) is now tracked as task #64.

## 13. Eval dataset composition audit (2026-08-26)

Prompted by a third-party claim (of unverifiable provenance — see
`feedback_benchmark-skepticism.md` memory for why that source itself was not trusted) that our
own IntelliJ eval dataset is skewed toward "where is X" queries. Checked independently, on our
own initiative, against the actual generator and data (not the third-party claim itself) — full
detail in `.plans/2026-08-26_eval-dataset-intent-coverage.md`.

**Confirmed, not refuted.** Of 1125 total cases (1065 + 60 multi-file):
- **986 (87.6%)** are mechanical `symbol`/`config`/`path` categories — the query is built
  directly by tokenizing the target file's own class/file/directory name (e.g.
  `DriverIllegalStateException.kt` → "where is driver illegal state exception implemented"). Pure
  lexical recovery by construction, not a semantic/intent test.
- **79 (7.0%)** hand-written `where-*` single-file-locate queries, **60 (5.3%)** hand-written
  `multi-*` "which files implement X" queries — both still fundamentally locate/identify queries.
- Only **139/1125 (12.4%)** require any reasoning beyond near-exact lexical recovery, and **zero**
  of those 139 are multi-hop, comparative, exact-string-lookup, near-duplicate-discrimination, or
  usage-pattern ("how do I") queries — verified by exhaustive grep across both files for all five
  shapes; every superficial match was a false positive (e.g. `CompileStepBeforeRun.java` matching
  "before" is a class-name coincidence, not a real multi-hop question).

**Expansion plan drafted** (not yet executed — task #65): 110-150 new hand-verified cases across
5 new categories, all example cases checked against the live `~/Work/intellij-community`
checkout (commit `693e76f0a37ade9509c9edcf505c446672c9c0b1`) via direct filesystem/grep checks,
not invented:
- **Near-duplicate discrimination** (40-50, hand-authored only, highest priority) — this is the
  most direct test of the §11 name-echo-distraction failure mode, e.g. distinguishing
  `UndoManagerImpl.java` (does the actual undo) from `CannotUndoReportDialog.kt` (only reports
  failure), or a 4-way Safe Delete family (`SafeDeleteProcessor` / `SafeDeleteHandler` /
  `SafeDeleteProcessorDelegateBase` / `JavaSafeDeleteProcessor`).
- **Multi-hop** (20-30) — e.g. "after RenameProcessor collects usages, which class rewrites each
  one" → `RenameUtil.java`.
- **Exact-string lookup** (20-30, semi-mechanical, extractable from `*Bundle.properties`).
- **Comparative** (15-20) and **usage-pattern "how do I"** (15-20) — reuse verified sibling pairs
  from the discrimination work under different framings.

None of these five categories can be safely bulk-generated the way `symbol`/`config`/`path` are
— doing so would reintroduce the exact lexical-shortcut problem this expansion exists to close.
